# FORYA on mobile

Two things now exist, from one codebase:

1. **An installable web app (PWA)** — live at https://forya.onrender.com. No stores, no accounts.
2. **Native iOS and Android projects** — `frontend/ios` and `frontend/android`, generated by
   Capacitor, ready to open in Xcode and Android Studio.

Both run the same React app. There is no second codebase to keep in step.

---

## 1. The installable web app

Nothing to do — it ships with every deploy. To install it:

- **iPhone/iPad:** open the site in Safari (it must be Safari), Share → *Add to Home Screen*.
- **Android:** open in Chrome, then the *Install app* prompt, or ⋮ → *Install app*.

It then launches without browser chrome, with the FORYA icon and a brand splash.

**What it caches, and what it deliberately doesn't.** The app shell, fonts and images are cached
so the app opens instantly and survives a dropped connection. The public catalogue and weather use
a network-first policy with short windows — a stale price is worse than a slow one. Anything
per-user — sign-in, moments, wardrobe, shared looks, the stylist — is **never** cached, so a shared
phone can't serve the last person's wardrobe out of the cache.

**Updates** are automatic: the service worker fetches a new build and applies it on the next
launch. `sw.js`, the workbox runtime and the manifest are excluded from the one-year static cache,
without which an installed app would pin itself to an old build forever.

### What a PWA can't do

No App Store or Play Store listing, so no store search traffic. iOS push notifications work only
once the app is installed to the home screen and are more limited than native. No deep native
hooks beyond what the browser gives — which matters most for wardrobe photos.

## 2. The native apps

### Before anything else: allow the shell's origin

The native app bundles the web assets locally, so its page origin is **not** your domain —
it's `capacitor://localhost` on iOS and `https://localhost` on Android. API calls are therefore
cross-origin and the server will refuse them until those origins are allowed.

In Render → Environment, set:

```
ALLOWED_ORIGINS=https://forya.onrender.com,capacitor://localhost,https://localhost
```

The production config check in `backend/src/env.ts` was taught to accept these; before that change
it would have rejected `capacitor://localhost` for having no http(s) scheme and the **server would
have refused to boot**. Don't remove them from the allowlist without also removing the app.

### Build and run

All commands from `frontend/`.

```bash
# Build the web assets pointed at the deployed API, then copy them into both native projects.
VITE_API_BASE=https://forya.onrender.com npm run build
npx cap sync

npx cap open android     # opens Android Studio
npx cap open ios         # opens Xcode — macOS only
```

`VITE_API_BASE` is what makes the native build work. On the web it's unset, so calls stay relative
and same-origin; in the shell there is no origin to be relative to, so it must be absolute. Build
without it and the app will look fine and fail every request.

Re-run both commands after any change to the web app — the native projects hold a **copy** of
`dist`, not a live link.

### What you need

| | |
|---|---|
| Android | Android Studio, any OS. Free to build and sideload. |
| iOS | **macOS with Xcode.** There is no way around this — Apple doesn't support building elsewhere. |
| Play Store | Google Play Developer account, $25 once. |
| App Store | Apple Developer Program, $99/year. |

Signing certificates and store credentials are yours to create and hold.

### Before the first submission

- **`appId` is permanent.** It's `com.forya.app` in `capacitor.config.ts`. Once an app is published
  under an ID you cannot change it — only ship a new app. Change it now if FORYA lands on a
  different domain.
- **Apple guideline 4.2 (minimum functionality).** Apple rejects apps that are just a website in a
  webview. This is why the build bundles the assets rather than loading the live site, so it opens
  offline and behaves like an app. Strengthen the case before review by adding something the web
  can't do — camera capture for wardrobe photos and push notifications for moment reminders are
  the obvious two, and both are Capacitor plugins rather than new screens.
- **Privacy details.** Both stores ask what you collect. FORYA holds an email, a name, a country
  and the moments people create. Have a privacy policy URL ready; neither store will take the app
  without one.

### Rules the V4 screens encode

These came from the handoff and are not negotiable in build:

- **No budget anywhere.** No cap field, no `/£150` denominator, no "within your budget" score, no
  over-budget dialog. Cost is information. (17 separate instructions in the document.)
- **No guest route.** Nothing in the catalogue is visible before authentication.
- **Ownership is explicit.** A piece is owned only once the user confirms it physically arrived.
  Selecting a brand during onboarding never creates a garment.
- **Four tabs, fixed:** Home, Moments, Discover, Wardrobe. Profile is a plain icon-and-label
  action at Home's top right — 44 pt target, no coloured ring, no enclosing pill.
- **One Moment form.** What, Where, Date, Time, optional dress code on a single screen, date and
  time side by side, primary action fixed above the safe area.
- **New-piece totals stay fixed** above the safe area while retailer lists scroll.
- **Three wardrobe collections stay distinct:** My clothes, Saved items, Saved looks.

Typography follows the handoff's contract exactly: Bricolage Grotesque 700/600/500/400 with
Instrument Serif Italic for the editorial word; headline 30/32.4, section 22/25.3, body 17/24,
primary action 17/21.25, field label 15/21, metadata 14/19.6 and 13/18.2, bottom tab labels
11/13.2, brand captions 10.5.

**Canonical fixtures** (use these exact numbers in build): new account — Oxford shirt £24,
chinos £45, loafers £65 = **£134**, 0 owned / 3 new. After the footwear swap to Oxford shoes
£860 = **£929**. Retailers split M&S (shirt, chinos) and Mytheresa (shoes).

Brand tiles carry sized artwork slots, not logos — official brand files are a client asset and
are dropped into the named slots.

**This link belongs in version control, not a chat.** The previous Figma file's URL was lost
because it lived only in a conversation. If the file moves or is replaced, change it here.

**Imagery.** Two editorial slots carry real photographs (the Today hero and the Moment-detail
look). Every garment slot carries line art drawn as vectors — jacket, coat, knit, tee, trousers,
boot, shoe, flat, tote, scarf — on a tonal ground, light-stroked on the dark capture screens and
filled rather than stroked below ~58px where strokes collide.

This is a deliberate split, not a stand-in: editorial moments are photographed, pieces are drawn.
Swapping the drawings for real cut-outs is a one-pass job once the assets are shot — they live in
`frontend/public/images`, and every slot is named (`IMG · cut-out 1`, `IMG · product hero`) and
sized for drop-in replacement.

## 4. What hasn't been done

- **No app has been compiled.** This environment has Java and Gradle but no Android SDK, and no
  Xcode or CocoaPods — iOS builds need macOS. The projects are generated and configured; the first
  real build happens on your machine.
- **No store accounts, certificates or signing keys.** Those need your identity and payment
  details.
- **No native plugins beyond status bar and splash screen.** Camera and push are the two worth
  adding, and both want a short design conversation first — where photos are stored, and what a
  notification actually says.
- **Icons** are generated from the FORYA mark by `frontend/scripts/make-icons.mjs` and
  `@capacitor/assets`. They're clean, but a designer should look before launch.
